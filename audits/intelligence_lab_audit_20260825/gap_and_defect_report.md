## Severity-ranked findings

### 1. BLOCKER — The 8-tab per-ticker detail modal is built almost entirely from field names that do not exist in the governed book
**Evidence:** `functionality_audit.md` §0 and §4 (all 8 modal tabs traced field-by-field); cross-validated independently in this pass by direct reading of `intelligence-lab/static/index.html:1085-1957` (main-table sort/render) and `intelligence-lab/static/index.html:2129-2547` (modal tab builders). Confirmed empirically: none of `sb_*`, `mv__*`, `wbs__*`, `doss__*`, `eil__*`, `garch__l3_*`, `qomega_*` exist as keys in any of the 1063 rows of `data/output/runs/20260824_220616/intelligence_lab/final_opportunity_book_20260824_220616.json` (Python-verified in this pass, see method above). The governed row does carry the equivalent data under the contract name in most cases (`wbs_grade`, `morning_execution_permission`, `eil_v3_verdict`, `garch_iv_tailwind_score`, `readiness_stage`, `convexity_score`, `ts_checkpoint_rule`, etc. — all confirmed populated on the reference run) — the UI simply never reads that name.
**Trader impact:** Opening any ticker's detail modal to check Stage Ladder, Morning Val, EIL, or the WBS/Convexity sub-panels shows "no data" / all-blank / a permanently-closed panel, even though the governed book the Lab itself just loaded contains real, populated values for those exact concepts. A trader cannot use the modal to verify readiness stage, morning-validation state, or EIL score — the tool is not simply stale, it is silently non-functional for these panels regardless of how current or complete the underlying data is.
**Contradicts roadmap:** Directly contradicts the audit brief's premise that `GOVERNED_FINAL_OPPORTUNITY_BOOK_V2` / `lab_signal_book_v2` is the single source of truth the UI renders — the UI was not updated when the 232-field contract superseded the legacy in-memory signal shape.

### 2. HIGH — `/api/kpi` scoreboard silently reports zero/None for most metrics under governed-book operation
**Evidence:** `functionality_audit.md` §1, `/api/kpi` — 2764-2867: keys on `mv_verdict`, `data_quality_state`, `no_match`, `signal_trust_score`, `mv_breakdown`, none of which exist in `FINAL_BOOK_FIELDS` or the reference run.
**Trader impact:** The KPI dashboard (execute/probe/fresh/stale/no-match counts, average trust score, average spread) looks like a working scoreboard but is computing over absent fields for every run served from the governed book — i.e. every current run. No error, warning, or zero-flag is shown; the numbers simply read as low/zero, which is indistinguishable from "the desk genuinely had a quiet day."
**Contradicts roadmap:** N/A (no roadmap claim about KPI accuracy verified) — flagged purely as a defect for the user-guide author to avoid endorsing this panel's numbers.

### 3. HIGH — EIL tab visually asserts "advisory, not blocking" while the same field can hard-veto a trade
**Evidence:** `attribute_inventory.json` record `eil_v3_verdict` (`defects[0].type = "AUTHORITY_MISREPRESENTED"`): `intelligence-lab/static/index.html:2449` hardcodes "Advisory mode active — EIL scored but not blocking" as the fallback message; `contracts/lab_control.py:1028-1030` — `if "BLOCKED" in source["eil_v3_verdict"]: flags.append("EIL_BLOCKED"); veto_flags.append("EIL_BLOCKED")` — directly contributes to `hard_vetoes`/`lab_tradeable=False`. The governed enum actually reachable for `eil_v3_verdict` (`{EXECUTE, EXECUTE_WITH_CAUTION, WATCHLIST, BLOCKED}`, per the same inventory record) never matches the four tokens the UI checks for (`EXECUTE_NOW, EXECUTE_WITH_CAUTION, EXECUTE_DEFER, STAND_DOWN_MICROSTRUCTURE`), so the "not blocking" message renders unconditionally, regardless of the field's true state.
**Trader impact:** The single UI surface presenting EIL to the trader states in plain language that EIL cannot block a trade. It can. This is the clearest authority-collision in the audit — advisory-presented data with real control-family power.
**Contradicts roadmap:** Directly contradicts the audit brief's authority-collision definition ("advisory data... rendered with equal or greater visual authority than the control family").

### 4. HIGH — `morning_gate.py` CHECK 1 fails open on missing `invalidation_price` (audit's suspected `live_price` fail-open was checked and NOT found) **[NEW]**
**Evidence:** `morning_gate.py:896-924` (`_check_invalidation`). Missing `live_price` is handled correctly: line 901-902 returns `passed=False`, and `morning_gate.py:1370,1402-1409` routes that to `verdict=FLAG`, `morning_execution_permission=WAIT`, `route=WAIT_LIVE_PRICE` — fail-closed, not fail-open. **This specific suspected defect is NOT confirmed.** However, a missing/zero/negative `invalidation_price` (`row.get("evening_invalidation_price") or row.get("invalidation_price") or row.get("invalidation_level")`) is handled at `morning_gate.py:909-910`: `if not invalidation or invalidation <= 0: return True, "WARN - no invalidation level on record; structure cannot be verified"` — i.e. `inv_pass=True`. Because `inv_pass=True`, none of the block/flag branches at `morning_gate.py:1376-1441` fire, and the `WARN` string is never appended to `flag_reasons`, `block_reasons`, or `unlock_condition`. A row with a valid live price but no invalidation level on record can therefore fall through the full `elif` chain to the final `else` at `morning_gate.py:1442-1453` and receive `morning_execution_permission="GO_LIMIT"` — a live-capital-eligible state — with the "cannot be verified" warning silently discarded.
**Trader impact:** A trade whose stop/invalidation level was never recorded can reach GO_LIMIT with no visible flag that its invalidation is unverified. This is functionally the same class of risk the audit brief anticipated (missing safety-critical input silently producing a favourable state), just on `invalidation_price` rather than `live_price`.
**Which governed field carries this:** `morning_execution_permission` (field 22) and `morning_execution_route` (field 23) — see `attribute_inventory.json` record `morning_execution_permission`, which was annotated with this finding during Phase 2 assembly.

### 5. MEDIUM — Legacy pre-governance WBS "missing-PCR-volume momentum bonus" defect is VERIFIED FIXED, but its fix is invisible in the UI
**Evidence:** `contracts/lab_control.py:1801-1834`. Code comment confirms the historical defect existed: "WBS files created before the missing-PCR fix silently substituted 1.0. That granted every PUT a five-point momentum bonus." Current code detects the legacy condition (`pcr_unavailable and direction == "PUT" and legacy_pcr_state_missing and not _is_missing(row.get("wbs"))`) and actively reverses it: subtracts 5 points from `wbs`/`wbs_f5_momentum`, recomputes `wbs_grade`, and sets `wbs_pcr_volume_state = "UNAVAILABLE_LEGACY_BONUS_REMOVED"`. For new-format data (where `wbs_pcr_volume_state` is already populated upstream) the correction is skipped by design, on the stated assumption that the upstream WBS producer no longer applies the bonus in the first place — this assumption was not independently re-verified against the upstream WBS/wall-break-scores producer in this pass (UNVERIFIED upstream, but irrelevant to current risk since the governed-materializer correction is a backstop regardless).
**Disposition:** **Known-defect check (a) from the audit brief is answered: the defect existed, and the current codebase actively corrects it.** This is a positive finding, not a live defect. Rated MEDIUM only because the correction (and the underlying legacy-format risk it guards against) is completely invisible to the trader — `wbs_pcr_volume_state` is never rendered anywhere in `index.html` or the JS patch file (`attribute_inventory.json` record `wbs_pcr_volume_state`, zero UI hits) — so a trader cannot see whether a given WBS score benefited from this correction, was penalised by it, or was never at risk.
**Trader impact:** None currently (the correction works), but the user guide must not claim the trader can see or audit this correction from the screen — they cannot.

### C. Fields displayed from intermediate pipeline files rather than the final book (bypass risk)
- `/api/orchestrator/manifest/*` and the "Run Health" tab read `final_run_manifest.json` (a distinct, separately-governed artefact — `write_final_run_manifest`), not the opportunity book. Classified in `functionality_audit.md` §1 as an *alternate governed source*, not a bypass risk, since it is itself a first-class governed producer output.
- `/api/monitor_positions`, `/api/log_exit`, `/api/capture_outcomes`, `/api/outcomes`, `/api/learning_feedback` read the SQLite trade journal (`data/journal/trade_journal.db`) — by design a post-entry ledger, not the pre-entry opportunity book; not a bypass risk.
- `/api/open_contracts` reads `vanguard.trade_contract` store — genuinely UNGOVERNED_SOURCE relative to the Lab book, and silently drops unparsable entries (`except: pass`, `intelligence_lab.py:2704`) with no trader-visible warning.
- The true bypass risk is not "a different file" but "a different field-naming convention within the same governed JSON payload" — i.e. Findings 1, 6, 7 above, where the UI reads pre-governance key names that happen to be absent from the very same governed row it already has in hand.

### D. Authority-collision surfaces
1. **EIL** (Finding 3) — advisory-presented, control-critical in fact. Highest-severity authority collision found.
2. **Convexity tab** (`functionality_audit.md` §4 TAB 4) — shows "No governed producer field was supplied" (`index.html:2323`) when `convexity_score`/`convexity_campaign` (governed fields 186-187) are in fact populated; this inverts the intended authority signal (implies data absence where there is data presence) but does not itself cause a false permission, so classified MEDIUM, not BLOCKER.
3. **Morning Val tab** (`functionality_audit.md` §4 TAB 6) — shows "No morning validation data for this signal. Run morning_validation.py to populate." even when `morning_data_state` and the `morning_execution_*` family are populated. This is visually equivalent to "control family absent," when in the reference run's EOD-prep context `morning_data_state="NOT_RUN_EOD"` for all rows is itself a legitimate, meaningful governed state (morning validation genuinely has not run yet for an EOD-prep run) — so the *message text* is misleading, but the underlying non-availability is often accurate for this particular run's pipeline stage. Still a defect: the UI cannot distinguish "morning validation genuinely not yet run" (`NOT_RUN_EOD`) from "morning validation ran and rejected" (`MISSING_DATA_DEFECT`/populated-but-negative), because it never reads `morning_data_state` at all — see Gap E below.

### E. Morning-vs-evening staleness disposition
The governed field `morning_data_state` (232-field contract, field 222) is specifically designed to distinguish "morning fields never written" (`NOT_RUN_EOD` for EOD-mode runs, or `MISSING_DATA_DEFECT` otherwise) from "morning fields written" (`AVAILABLE`). **The UI never reads this field** (`attribute_inventory.json` record `morning_data_state`, `"displayed": false`). Instead, the Morning Val modal tab (Finding under D.3) infers presence/absence purely from whether its own (absent) legacy `mv__*` keys are populated — which is always false under governed data — collapsing all three real states (never-run / run-and-negative / run-and-positive) into one identical "no morning validation data" message. **Disposition: the seven-state distinction the audit brief requires is present at the data layer (`morning_data_state`) but is not enforced or surfaced anywhere in the UI.**

### F. Missing-data semantics conformance — the seven canonical states
Checked against `attribute_inventory.json`'s `enum_values_observed` across all 232 fields, cross-referenced with the producer code read directly in this pass (`contracts/lab_control.py` `opportunity_book_row` and `_recompute_governed_lab_fields`):

| State | Produced in code? | Observed in reference run? | Disposition |
|---|---|---|---|
| `AVAILABLE` | Yes — `contract_data_state`, `ev3_data_state`, `wbs_data_state`, `garch_data_state`, `convexity_data_state`, `morning_data_state`, `trigger_data_state` all use it. | Yes, on 12 fields. | **Enforced.** |
| `NOT_APPLICABLE` | Yes, but only ever as an extended/suffixed variant — `NOT_APPLICABLE_NO_SELECTED_CONTRACT` (`contract_data_state`), `NOT_APPLICABLE_NOT_SCORED` (`wbs_data_state`) — the bare token `NOT_APPLICABLE` was not found. | Yes (as the extended variants), on 5 fields. | **Partially enforced** — the *concept* is used consistently but the *literal enum token* the brief specifies is never emitted verbatim; classify as ENUM_MISMATCH (naming drift, not a missing-semantics gap). |
| `NOT_EVALUATED` | Yes — e.g. `ev3_advisory_state` default in `morning_gate.py:1122-1127`, and observed in `advisory_flags`/`pcr_vol_status`/`pcr_vol_missing_reason`/`direction_conflict_status`. | Yes, on 4 fields. | **Enforced.** |
| `STALE` | Referenced in code only at the run-manifest level (`stale_flags`, `mv_live_validation_state in {"NO_LIVE_DATA","STALE"}` at `contracts/lab_control.py:1025`) — never assigned as a `FINAL_BOOK_FIELDS` field value in `opportunity_book_row` or `_recompute_governed_lab_fields`. | **Not observed on any of the 232 fields in the reference run.** | **Not enforced at the book-field level.** A trader cannot tell, from any governed book field, that a piece of data is stale rather than simply absent — staleness lives only in the separate `final_run_manifest.json` artefact (`stale_flags`), which is not part of the 232-field contract and is only surfaced via the Run Health tab / `/api/orchestrator/*` routes, not per-field. |

**Overall disposition for the user guide:** three of seven states (`AVAILABLE`, `NOT_EVALUATED`, and — with an important literal-token caveat — `NOT_APPLICABLE`) are meaningfully and consistently enforced at the field level. `STALE` has no field-level representation at all in the 232-field contract (it lives only in the separate run manifest). `MISSING_DATA_DEFECT` exists in code but was not exercised by the sampled run. `NEUTRAL` and `ZERO` are not established conventions — they each appear on at most one field and (for `ZERO`) the single observed instance is doubtful. The user guide must not claim uniform seven-state missing-data semantics across the Lab; it should describe the `*_data_state` field family (`contract_data_state`, `ev3_data_state`, `wbs_data_state`, `garch_data_state`, `convexity_data_state`, `morning_data_state`, `trigger_data_state`) as the actual, narrower, working mechanism, and note that most other governed fields simply render blank/`—` when absent with no distinct state marker at all.
