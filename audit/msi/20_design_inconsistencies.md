# MSI v1.1 — Design Inconsistencies and Design-vs-Implementation Divergences

**Date:** 2026-08-30. Report only — not resolved here, per task instructions. Compiled from all five test-agent reports.

## 1. §8.2 vs. §18/§24 quote-quality and size-quality label naming

The design's own arithmetic (§8.2's mid/spread formulas, MISSING/OBSERVED_ZERO/INVALID_SIZE size rules) is followed correctly by the implementation. But §24's literal enum-value table is not:

- Quote quality: §24 specifies `CROSSED` for bid>ask; the code emits `INVALID` at every call site, consistently, and the implementer's own regression suite (`tests/test_msi_agent1_data_foundation.py:52`) codifies `INVALID` as the *expected* value — this is a deliberate implementation choice, not a slip.
- Size quality: §24 specifies `OBSERVED` for a positive numeric size; the code emits `OBSERVED_POSITIVE` at 4+ independent call sites.
- The zero-bid case (§8.2's `ONE_SIDED` vs. §18's prose "observed zero-bid preservation as ZERO_BID/non-executable") was checked directly: this is **not** an internal contradiction — the design's two passages describe the same record's two different fields (`quote_quality=ONE_SIDED` and a separate non-executable flag), and the code correctly implements both. Reported here only to close out the specific check the task brief asked for; it is not a finding.

This is a genuine implementation-vs-design divergence pattern (not a design self-contradiction): the code consistently followed a different naming convention than §24 specifies, across every module, in both new naming choices and in the pre-existing test suite that encodes them as expected.

## 2. §7.4 vs. §16.3 — freshness centralization

§8.7 requires every bundle to carry a `freshness_map`. §16.3 requires that the single `canonical_data/session_clock.py` service "owns" freshness and that "consumers cannot recreate these rules locally." The implementation satisfies the field-presence half but not the centralization half: `evaluate_freshness()` is correct and exists in the one canonical location, but has zero production callers anywhere in the codebase. `freshness_map` is populated instead from ad hoc row-level fields, including a hardcoded `"UNASSESSED"` string literal (`marketdata_response.py:141`). This is not a contradiction between two design sections — both are internally consistent — but the implementation resolves the tension between "populate the field" and "use the shared service" by doing only the former.

## 3. §23's literal SHA-256 algorithm for `ms_evidence_id`

§23 states `ms_evidence_id` is "SHA-256 of ticker, session, algorithm version, parameter version and ordered input dataset IDs." The implementation uses `uuid5(NAMESPACE_URL, lineage)` — RFC 4122 `uuid5` is SHA-1-based, not SHA-256, and is not a 64-hex-character digest. The *behavioral* requirements the design cares about (deterministic, version-sensitive, order-sensitive) are all met by `uuid5` — but the literal algorithm named in §23 is not what was built, and the lineage string additionally folds in `run_id` and `input_hashes`, which §23's rule does not list as inputs.

## 4. §11 — "the governed book becomes `lab_signal_book_v3`"

In practice, two differently-versioned books coexist: the Lab's own live book (`contracts/lab_control.py`, `intelligence-lab/intelligence_lab.py` — the §22-named "Lab materialisation" owners) still stamps `lab_signal_book_v2`; `lab_signal_book_v3` is produced only by `contracts/interpreter_handoff_materializer.py` as a separate, derived, handoff-only artefact. §11's phrasing ("the governed book becomes...") reads as describing one book's identity changing, not two books with different version tags coexisting permanently. This is an implementation deviation from the design's apparent intent, not a design self-contradiction — but it is exactly the kind of thing R-06/R-09's "Lab and Interpreter match" acceptance criterion (§20 (9)) would need reconciled before a live cycle could confirm 100% match.

## 5. §22 module map — two named modules do not exist under their specified paths

`canonical_data/market_observation_service.py` and `market_structure/contracts.py` are both explicitly named in §22 as new modules to be created. Neither exists. The responsibility for the first appears distributed across `canonical_data/market_observation_resolver.py`, `marketdata_response.py`, `intraday_bars.py` and `stage_publisher.py`; the responsibility for the second appears to live inside `market_structure/service.py`/`profile.py`. This is not a design self-contradiction, but it is a deviation from the design's explicit module-map instruction, and it is not merely cosmetic: F-08 and W-01 show the *consequence* of at least one of these relocations is an actual field-propagation gap (underlying NBBO and option-contract sizes are computed and then dropped), not just a naming difference.

## 6. §19 MSI-0's own entry-point-recording requirement was not fulfilled

§19 MSI-0 states: "record the current production baseline commit/hash and every intended modified file" and §22's closing paragraph requires "MSI-0 records the exact active entry point and function for every row before edits begin." No such per-row record exists anywhere in the repository — only a file-hash-only backup manifest (`backups/msi_v11_prechange_20260830_110913/MANIFEST.md`) and a prose implementation record with no function-level citations. This does not block testing (the code can be read directly, and every test agent did so), but it means there is no authoritative source to check specific-function claims against; every citation in the findings register was independently derived by the test agents, not cross-checked against an MSI-0 record, because none exists.

## 7. Seven of eight feature switches enabled simultaneously with zero completed production cycles

§19 MSI-8 and §28 step 6 both state switches should be enabled sequentially "never activate all switches at once without phase evidence." `config/msi_runtime.json` currently has `v2_capture`, `cds_resolver`, `minute_bars`, `structure`, `lab_v3_view`, `macro_advisory`, `interpreter_resolver` all `true` simultaneously (only `screen_adapter` is off), while zero evening→morning→Lab→Interpreter cycles have been completed (confirmed by `07_run_artefacts.md`'s precondition-failure finding). This is a process deviation from the design's own stated sequencing discipline, worth flagging even though it may be a deliberate "controlled production cycle 1" decision by the implementer (their own record labels the deployment state `CONTROLLED_PRODUCTION_CYCLE_1`) rather than an oversight.

## 8. The implementer's characterization of the golden-fixture regression failure is UNVALIDATED, not confirmed

`audit/msi_implementation/MSI_IMPLEMENTATION_RECORD_20260830.md` states the one known regression-suite failure (`test_priority_rank_byte_identical_to_frozen_baseline`) is "fixture drift, not an MSI field or authority regression" and that "the production implementation was not changed to satisfy this stale data fixture." The independent regression agent ran a non-destructive causality probe and found that `intelligence-lab/intelligence_lab.py` — imported live by the very regeneration script this test re-executes against the frozen historical baseline — was modified today (mtime 13:20, after the 11:09 pre-change backup) as part of MSI's own "Lab materialisation" module-map ownership. Substituting the pre-MSI backup copy of just that one file broke the regeneration entirely (0 rows), due to cross-module coupling with other files also touched by MSI, so clean causal isolation was not achieved — the result is inconclusive, not exculpatory. **The implementer's claim that this failure is unrelated to MSI is asserted, not proven, by the evidence available**, and the code path the test exercises was directly touched by MSI today. This deserves a signed, deliberate re-verification before being accepted as pre-existing drift.

## 9. Two regression-suite failures newly found, not disclosed in the implementation record

`test_morning_handoff_finalizer.py` (2 failures, `MATERIALIZER_MISSING_IDENTITY`) and `test_pipeline_interpreter_trusted_source.py` (2 failures, path-resolution) are both suites explicitly named in the design's own §18 regression-suite list ("Morning handoff finalizer," "Pipeline Interpreter handoff guard"). The implementer's own verification-evidence section claims these categories as passing ("Morning finalizer, Lab handoff and compatibility tests: 35 passed / 0 failed," "Pipeline Interpreter automation/compatibility regression: 65 passed / 0 failed") without disclosing these specific failures. It's possible these suites were passing at the time the implementer's own count was taken and something changed afterward (the working tree is not frozen — other agents' scratch work and file mtimes suggest ongoing activity), or the implementer's suite selection differed slightly from the independently-built list here. Either way, the discrepancy between the claimed clean baseline and this pack's independently-reproduced 6 new failures is real and reportable.
